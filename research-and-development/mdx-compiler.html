NoteBooks MDX compiler and renderer

Status: Implemented with @mdx-js/mdx 3. MDX expressions and React components execute during server rendering only for explicitly trusted repositories. The mdx-rendering Supabase feature flag is seeded to false.

This file is a live compiler fixture: its expressions, React elements, equations, callouts, diagrams, outline, and search metadata are checked by NoteBooks-Framework/test/mdx-compiler.test.ts.

What “executable MDX” means here

The compiler parses MDX into a React component, runs it with the React JSX runtime, and renders the result to static HTML on the server. JavaScript expressions inside MDX are evaluated. Standard Markdown and JSX can be mixed in one document.

The generated page is static HTML; it is not hydrated as a React application. JSX event handlers and client-only hooks do not become interactive browser behavior. Use the existing reader runtimes for interactive Mermaid, TikZ, Desmos, and Desmos 3D content.

MDX is executable code, not a safe format for arbitrary repositories. Trust is opt-in and has two gates:

  1. The Supabase feature_flags row named mdx-rendering must have enabled = true. The migration creates this row with false.
  2. The exact owner/repository must be included in the server-only TRUSTED_MDX_REPOSITORIES comma-separated environment variable.

For example:

TRUSTED_MDX_REPOSITORIES=notebooks/developer-docs,notebooks/approved-lessons

Treat every trusted repository writer as having the ability to execute server-side JavaScript with the application process’s privileges. Never add a repository whose contributors are not trusted. If either gate is off, .mdx is rendered by the ordinary non-executing Markdown renderer.

Rendering pipeline

  1. /read validates the repository, branch, and .md, .markdown, or .mdx path, then retrieves its catalogued source.
  2. For .mdx, the server reads the cached Supabase mdx-rendering flag. If disabled, it follows the Markdown path. If enabled, the repository must match the explicit trust list.
  3. compileMdx compiles the document with @mdx-js/mdx. JavaScript imports and exports are rejected; use the application component registry instead.
  4. renderMdxNote uses a bounded in-memory cache for compiled modules (64 entries / 8 MiB), runs the module using React’s JSX runtime and an explicit component map, then uses renderToStaticMarkup.
  5. Reader components add heading IDs/tree, searchable block IDs/index, repository-relative link rewriting, callouts, KaTeX output, and diagram placeholders. The normal reader client initializes supported diagrams.

Compilation is asynchronous; use await renderMdxNote(source, sourceInfo). renderNote remains the synchronous renderer for .md and .markdown.

The renderer adds reader metadata to h1-h6, p, ul, ol, blockquote, pre, table, and hr; it rewrites relative URLs in a and img. All other intrinsic tags render through React’s default JSX behavior. Attributes and children become server-rendered HTML. Since the output is static, event handlers are not browser interactions.

Uppercase custom component names must be provided in the application component registry. renderMdxNote accepts an optional MDXComponents map for application-owned React components; no source-level import is needed or allowed. The built-in components are:

Lowercase native HTML tags are React intrinsic elements; uppercase elements are registered React components. Import/export statements are deliberately rejected so an MDX file cannot load arbitrary modules. Expressions remain executable in repositories that pass both trust gates.

Supported Markdown and note features

MDX supports standard Markdown constructs including headings, paragraphs, emphasis, links, images, lists, blockquotes, inline code, and fenced code. Its compiler also enables GFM tables/task lists/strikethrough and dollar-delimited math. The .md and .markdown pipeline separately supports Obsidian wiki links and media embeds, highlights, tags, comments, standalone and blockquote callouts, footnotes, subscript, and superscript; these extensions are not yet all wired into the MDX pipeline.

Repository-relative links and media paths use the existing /read and /api/media routes. MDX headings create the reader outline tree; rendered text blocks populate the reader search index. Fenced diagrams are supported by the normal Markdown renderer; in MDX, use the registered diagram components.

Error behavior and safety boundary

  • MDX syntax errors and rejected import/export statements surface as compile errors with source locations when available. They are not silently dropped or interpreted as successful output.
  • An untrusted repository is rejected before compilation/evaluation when the database flag is enabled.
  • The feature flag lookup fails explicitly if the Supabase setting is missing or cannot be read; it is not treated as enabled.
  • The normal Markdown renderer keeps raw HTML disabled. It is the non-executable fallback when MDX rendering is disabled.
  • Trusted MDX executes in the server process. The trust list is a code-execution allow-list, not a cosmetic display preference. Do not configure it from client input, repository metadata, or untrusted environment sources.

To add a built-in component, implement it in the MDX renderer component map, add tests for its React output and metadata, add a live example here, and document its props and whether it has a reader-side runtime. Application-provided components must be imported by application code and passed through the registry.

Tests and performance

Run the focused compiler tests and the local benchmark from NoteBooks-Framework:

pnpm exec vitest run test/mdx-compiler.test.ts test/markdown-renderer.test.ts
pnpm mdx:bench

The benchmark warms up and reports median, p95, and mean times for uncached compilation and full server rendering of this document after compiled-code caching is warm. It records source size and Node version. One local run on Node v22.23.1 measured 10,590 source bytes / 143 lines: compile median 64.662 ms (p95 93.106 ms); cached full-render median 22.300 ms (p95 31.640 ms). These are a noisy, hardware- and runtime-dependent sample, not a production latency guarantee.

The fixture tests execute an expression, render an application-provided React component, reject imports/exports, verify the trusted-repository gate, check built-in callout/math/diagram output, and compile this document itself. Existing Markdown renderer tests continue to guard .md and .markdown behavior.
