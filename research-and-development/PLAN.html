Stage 4 — Design and implement safe queue idempotency

Audit references: Q-01, Q-02
Files to inspect/change as needed: NoteBooks-Framework/src/lib/qstash.ts, src/lib/repository-update-queue.ts, src/app/api/webhooks/repository-update/route.ts, src/app/api/cron/repository-reconciliation/route.ts, workflow/repository-update.ts, and focused tests.

Status: Implementation completed and documented in QSTASH-OPERATIONS.md; Q-01 in AUDIT-QSTASH-SUPABASE.md records the resolved implementation. Production verification is not done.

Design gate

Before adding an idempotency key:

  • Identify whether the incoming GitHub workflow provides a stable delivery/event ID and whether reconciliation has a run ID or scheduled occurrence ID.
  • Confirm how QStash enqueueJSON supports the deduplication option in the installed SDK and FIFO queue mode.
  • Scope the key to one event, commit, or reconciliation occurrence. Never use a static repository/branch key: QStash deduplication may suppress that key for 90 days, blocking legitimate future messages.
  • Define how two distinct commits, repeated deliveries of one event, and later daily reconciliation are treated.
  • Keep QStash publish deduplication distinct from worker-side idempotency and database catalog locking.

Implementation after design approval

  • Add deterministic event/run identity to the enqueue contract and validate it at the worker boundary.
  • Prevent duplicate work only where identity proves the messages represent the same update. Do not silently drop valid later repository updates.
  • Preserve bounded concurrency and current queue sharding unless measurements and a concurrency review justify changing them.

Verification

  • Test duplicate delivery of the same event, a later event for the same repository, different repositories in the same shard, and reconciliation after a webhook.
  • Verify the original queue acknowledgement response still means “queued”.
  • Test QStash retry and failure paths without production credentials.

Completed verification

  • The Framework implementation supplies push and reconciliation workflow run ID plus attempt, validates the queue job at publisher and worker boundaries, and publishes a bounded SHA-256 deduplicationId scoped to repository, branch, source, run ID, and attempt.
  • The existing five queue shards, reconciliation batch limit, five QStash retries, and queue acknowledgement semantics remain unchanged.
  • Tester passed: pnpm exec vitest run test/repository-update-routes.test.ts test/repository-reconciliation-route.test.ts test/repository-update-queue-idempotency.test.ts (3 files, 14 tests).
  • git diff --check passed.
  • Production QStash delivery, deployed signing keys, live retries, DLQ, backlog, and Supabase/Redis state were not verified.

Stage 5 — Make worker/index failures recoverable

Audit references: Q-02, S-02
Files: NoteBooks-Framework/workflow/repository-update.ts, src/lib/public-indexes.ts, sync-run schema/migrations only if required, and focused worker tests.

Changes

  • Add focused tests for catalog sync success followed by Redis rebuild failure, and for a retry that later rebuilds the indexes.
  • Distinguish repository catalog outcome from public-index outcome in logs and sync-run data, so a failed rebuild cannot be mistaken for a fully healthy public state.
  • Preserve a repair path when Redis is empty or indexes are stale even if the repository commit SHA has not changed. Do not skip index rebuilding solely because the source commit is unchanged.
  • Decide whether orphaned running sync-run records need a bounded cleanup or stale-run recovery after observing realistic worker termination behavior.
  • Avoid a database migration unless tests/source inspection demonstrate the current schema cannot represent the required outcome.

Verification

  • Exercise failure before catalog sync, after catalog sync, during index rebuild, and after successful retry.
  • Confirm the public index can be rebuilt after Redis loss without requiring a new source commit.
  • If a migration is needed, replay it in a disposable local/test database and review it before any production deployment.

Status: Completed for tested worker behavior; orphaned-run recovery remains deferred. workflow/repository-update.ts distinguishes catalog and index outcomes with catalog_sync_failed and index_rebuild_failed. It rebuilds indexes even when the source commit is unchanged, so a retry can repair an index failure without a new commit. A failed worker response remains HTTP 500 for QStash retry, and the focused retry test verifies a later successful rebuild. No migration was needed. Verification passed: pnpm exec vitest run test/repository-update-workflow.test.ts test/repository-update-routes.test.ts test/repository-update-queue-idempotency.test.ts test/public-indexes.test.ts --reporter=verbose (4 files, 20 tests); focused test ESLint and git diff --check also passed. Cleanup or recovery of orphaned running sync-run records was deliberately not implemented. These results do not verify real Redis, Supabase, or QStash operations; see Q-02 and S-02.
